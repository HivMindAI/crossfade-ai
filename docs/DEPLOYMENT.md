## Configuration

Any publication of a reviewed candidate requires a fresh, explicitly owner-authorized file manifest and a separate review. [PUBLICATION.md](PUBLICATION.md) is a historical record, not a procedure for this release. [Bridge Discovery](BRIDGE_EXPERIMENT.md) has one owner-observed artist-only result; it does not change the production route or its shared quota guard.

1. Deploy the existing `feature/crossfade-mvp` commit only after review. Do not merge `main` as part of setup.
2. Keep `QLOO_API_KEY` in the hosting provider's **server-side secret settings**. Never use `NEXT_PUBLIC_`, a repository file, browser storage, or a build log for this value. The current hackathon-key flow permits only `https://hackathon.api.qloo.com`; leave `QLOO_API_ORIGIN` unset or set it to that exact origin, and stop for contract review if the issuer provides another host. Keep `QLOO_LIVE_ENABLED=0` (or unset) until the authenticated and public-abuse gates below pass. Synthetic mode needs no key or Redis.
3. Build with `npm ci && npm run build`, start using the platform's Next.js Node integration or `npm run start`, and require HTTPS on the public hostname. Do not use a static export for `/api/plan`.
   Set server-side `CROSSFADE_SITE_ORIGIN` to the exact browser origin, including scheme and nondefault port (for example, `https://example.com` on a reviewed public host or `http://127.0.0.1:3100` for the private P1 run). The production Origin guard validates this setting, rejects malformed or wildcard values, and never derives trust from request `Host` or forwarding headers. A missing setting retains the strict `request.url` comparison, which can reject valid requests when a Next.js server reconstructs an internal hostname.
4. Claim a [$0 Upstash Redis database](https://upstash.com/pricing/redis) under the account owner's control. Do not use an unclaimed temporary database for a live demo. Put its HTTPS REST URL and **standard write token** in server-only `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`; the application accepts only `https://*.upstash.io` origins. Never put the token in a client variable or URL query. Upstash's [REST API supports POSTed Redis commands and scripting](https://upstash.com/docs/redis/features/restapi). The code makes one atomic `EVAL` reservation before any live Qloo call. Missing or unhealthy Redis fails closed with 503; an exhausted shared budget returns 429. The [Milestone 11 handoff](BACKEND_HANDOFF_M11.md) gives an isolated-key owner verification that does not consume the real plan allocation.
5. Obtain the issued Qloo account's actual hourly, cumulative/period, and any shorter rate allowance, plus reset/expiry times. Set `QLOO_LIVE_PLANS_PER_HOUR` to an integer from 1 to 10 that is **no larger than** `floor((remaining hourly Qloo attempts allocated to this app) / 24)`; use `1` for the first local plan. Also require at least 24 uncommitted attempts in every cumulative limit. Reserve capacity for other uses of the key. Each admitted planner run can make up to 24 retry-inclusive Qloo attempts; the Redis counter conservatively charges a full run even if fewer attempts occur. A 60-minute window begins with the first accepted run and is shared by all instances using the same database/key. This hourly Redis key does **not** enforce a separate monthly allowance or know about external key usage; the [backend handoff](BACKEND_HANDOFF_M11.md) specifies the future atomic cumulative guard. If any applicable allowance is unknown or below 24 attempts, leave live planning disabled.
6. On the chosen public host, configure a provider-enforced per-source rule for `POST /api/plan` before enabling live mode. [Vercel WAF rate limiting is available on Hobby](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting), but its current documentation permits **one** rate rule per Hobby project and presents pricing; the owner must verify $0 eligibility and account access before relying on it. If eligible, start with an IP-keyed rule of no more than five planning requests per minute per provider-observed source IP, then test allowed traffic, a sixth-request 429, and NAT/shared-IP behavior on the actual hostname. Adjust only after observing legitimate demo traffic and quota consumption. Application code must not use caller-supplied `X-Forwarded-For`, `X-Real-IP`, or `Origin` as authenticated identity. The app's process-local emergency windows are now separate: 60 synthetic or 15 live plans per minute per instance. They still allow one client to exhaust a mode's local window; the provider rule is mandatory. The atomic Redis budget is an independent cross-instance ceiling, not a per-source rule. Its isolated reservation was owner-verified; no public provider rule has been verified.
7. Restrict deployment logs to safe status/error codes. Do not log Qloo request headers, raw responses, full user interests, Redis tokens, or secrets. Monitor 429, timeout, and upstream errors without exposing payloads. A cross-request plan cache is deferred until privacy, key scoping, and expiry are specified and tested.

- **Authenticated integration:** The owner completed the bounded Search/Movie/Book shape diagnostic and one fixed P1 with no complete path. A separate artist-only Bridge run established shared-filter coverage, not affinity or a complete plan. Any additional [live journey](LIVE_JOURNEY.md) requires separate account-owner approval and allowance confirmation; repeat the [bounded smoke](QLOO.md) only for a new contract question. - **Shared quota:** The owner reported a passing isolated test of Redis atomic reservation, expiry, exhausted response, and cleanup on a disposable key. It does not establish public Live safety. Application 429/503 mapping remains separately covered by offline tests. The issued key's Qloo quota, hourly and cumulative allowance, reset windows, and other clients' usage remain unverified; the current code only enforces the hourly ceiling and cannot count other clients' usage. Public per-source abuse control is also unverified. Never test a quota failure by sending an unapproved live Qloo plan.
- **Scheduling:** Obtain trustworthy film runtime in minutes and rating independently before treating a conceptual result as a duration-verified schedule. Check rights, availability, and venue separately.
- **Public deployment:** After rate controls are in place, verify HTTPS, origin behavior, error states, mobile layout, and synthetic/live provenance on the actual public URL. This is a distinct gate from local or authenticated API testing.
- **Activation:** Only after those checks, the account owner may set `QLOO_LIVE_ENABLED=1` server-side. Revert it to `0` if rate limits, response contracts, or safety controls fail.
- **Submission:** Update the Devpost text and PR validation record with only observed results; the account owner makes the final submission.

Give judges a direct feature-branch URL if this remains unmerged, and confirm that this satisfies the organizer's repository requirement. A reviewed merge or default-branch change would improve the root landing page but needs separate authorization.
