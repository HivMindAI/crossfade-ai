# Architecture and decision record

## Boundaries and provenance

The browser sends a validated plan request to the Next.js server route. The route chooses a server-only Qloo client or a clearly labeled synthetic fixture source. The key never enters browser code. Search resolves input interests; Insights returns separate artist, movie, and book result sets for each audience. Candidate identity is the intersection of stable entity IDs, never a guessed name match. Qloo results, recognized per-result influence signals, algorithmic rank totals, hard constraints, missing evidence, and creative experience text remain distinct in the response and UI.

The synthetic catalog is invented for development. No test fixture is a captured or verified Qloo response.

Search item validation is shared by the server client and bounded smoke in `src/lib/qloo-search.mjs`. It requires explicit category membership in a nonempty string `types` array, rejects conflicting recognized primary categories and duplicate metadata, preserves opaque IDs and first-result ordering, and ignores popularity. Insights has a separate nested entity envelope and shares its own strict page classifier with the smoke. The owner observed valid Artist Search and five each of Movie and Book Insights with generic `type` plus exact domain `subtype`; production accepts these forms and rejects ambiguous metadata. The owner also ran one fixed two-audience P1 plan, which ended with zero shared IDs in the bounded pages and no complete path. A separate artist-only Bridge experiment found 20 jointly returned filtered IDs, without verifying positive affinity. Bridge is not imported by the production route. Movie/Book Search and a complete live three-domain recommendation remain unverified.

## Bounded conditional agent cycle

The deterministic planner follows PLAN → SELECT TOOLS → EXECUTE → EVALUATE → VERIFY. It resolves up to six named interests and schedules six baseline Insights calls with at most three concurrent source calls. If a domain lacks an eligible shared candidate, it records why. A full 20-result page makes one documented recovery action useful: request page two only for the full audience side(s). Short pages do not trigger redundant calls. Recovery is capped by a 16-logical-call budget, and the Qloo transport separately caps actual HTTP attempts, including retries, at 24. A budget shortfall is explicit; no hard constraint is weakened. Rejection or changed inputs starts a new bounded run, with prior rejected IDs preserved.

This is tool-using deterministic orchestration, not an LLM. There is no paid model dependency. The trace names the selected tool, failed domain, recovery action, and final verification outcome.

## Negotiation policy

For each domain, the planner keeps shared entities whose **known** metadata and explicit rules permit them. It enumerates all three-act combinations from at most two 20-result Insights pages per domain (at most 40³ = 64,000 tuples) and sums rank positions within each audience's own result lists. If any duration-verified combinations exist, they take precedence over conceptual combinations; otherwise only clearly labeled conceptual paths are considered. A plan is Pareto-dominated when another plan is no worse for either audience and strictly better for one. Sorting tuples by A's sum, then B's sum, then ID and retaining a point only when its B sum improves on all earlier points produces the exact two-dimensional frontier in O(N log N) time. It avoids losing extreme trade-offs to a top-12 cutoff. From the frontier, the fairness-first path minimizes the worse rank sum, then imbalance, then total rank. An A-favoring path is shown only if it improves A's sum while worsening B's relative to the fairness path; the B-favoring path uses the converse. Deterministic entity-ID ties ensure repeatable output. When those genuine trade-offs do not exist, the UI shows fewer paths and says why.

Rank totals are ordinal algorithmic scores, not satisfaction probabilities or comparable Qloo affinity values. No source result is promoted to a causal explanation.

## Agreement diagnostics and evidence receipts

The same `inspectDomain` filter used to build eligible candidates counts unique shared IDs and classifies observed blockers: empty source results, no shared IDs, explicit exclusion, conflicting metadata, invalid runtime, film limit, total-program limit, or rating. The orchestrator records whether page-two recovery was unnecessary, unavailable, attempted, or skipped because the logical-call budget could not cover it. When any required domain blocks the plan, the response contains no full option; it retains only up to two eligible candidates per domain as explicitly labeled partial evidence. The conclusion is limited to the retrieved candidate pool. The suggested next action follows the observed blocker and never waives a hard rule.

Each candidate carries an identity, source label, both within-audience ranks, checked rule list, unverified conditions, and evidence limitations. Rejection feedback identifies the removed ID, a replacement where one exists, and the revised result status. These receipts do not treat rank as probability or missing Qloo explainability as a value.

The synthetic-only evaluator captures the post-recovery matrix in memory and compares the product with a simple feasible baseline using exactly that matrix and request rules. It checks coverage, worst-audience rank sum, diversity, known violations, provenance completeness, repair exclusion, source calls, and elapsed time. A single-path baseline cannot have directional alternatives. The fixture comparison is a regression tool, not evidence of live Qloo performance or human satisfaction.

## Feasibility and missing evidence

Milestone 8 keeps provider counts and rank positions before local exclusion checks. Deduplicated second-page entities retain their original offset; absence of a candidate or an empty response has no inferred filtering cause. Per-side retrieval status records an unexpanded full page, a reached page cap, or an observed short page. All are bounded observations, and a short page does not prove exhaustive retrieval. Workers drain in-flight calls and stop queued dispatch after the first observed failure.

The browser validates successful planner responses with the existing Zod dependency before rendering: expected shape, source/mode, domain order, status/schedule consistency, known constraints, and rejection exclusions. Invalid responses become an error state. A failed repair retains the rejection and names the failure; an incomplete plan can show a partial alternative for the rejected domain without claiming it is a complete replacement.

The proposed agenda reserves 20 minutes for listening, 10 for transition, and 15 for discussion. A path is duration-verified only when known film minutes plus that 45-minute agenda fit both the film and total-program limits, and a known rating is allowed. A known rule violation or conflicting metadata excludes that film. Missing runtime/rating metadata does **not** pass the gate: it allows only a conceptual experience without a certified total or schedule, and the missing fields appear in the gap and trace. The public Qloo reference does not document a runtime field with minute units, so the live adapter intentionally leaves film minutes unset pending authenticated contract verification. Screening rights, availability, ticketing, and venue are separate human checks.

## API and security behavior

The route streams request bodies with a 16 KiB cap, validates JSON and schema, checks browser origin in production, ignores `X-Real-IP` and `X-Forwarded-For` as untrusted identity, and applies separate process-local emergency windows (60 synthetic or 15 live plans per minute). Synthetic traffic cannot spend the live local window. A single client can still exhaust a process window for its mode; a provider edge rule using provider-verified source identity must be tested before public live use. Browser abort signals pass through the route, planner workers, Qloo fetches, and retry waits. Work stops before the next dispatch once an abort is observable; in-flight work and a shared quota reservation are never refunded. Whether client disconnects abort a route handler depends on the deployed Next.js/hosting runtime and must be measured there. Live planning additionally requires a server-side key, `QLOO_LIVE_ENABLED=1`, and an **atomic shared hourly plan reservation** in an approved Upstash Redis REST database. The quota guard fails closed before any Qloo call when configuration, Redis authentication, response validation, or connectivity fails. Its Lua script admits at most the configured number of plans across instances in a fixed 60-minute window beginning with the first admission; each admitted plan conservatively reserves the application's maximum 24 Qloo HTTP attempts. The account owner must derive the plan ceiling from the issued Qloo allowance and verify the guard in the chosen provider before public activation. The per-process window remains a local brake; a provider WAF rule can add per-source protection but cannot replace the global quota. Cross-request caching remains deferred pending privacy, key-scoping, and expiry review. The Qloo client accepts only the hackathon Qloo HTTPS origin for hackathon-issued keys, refuses redirects, and returns safe errors for authentication, malformed responses, timeouts, long rate-limit delays, and budget exhaustion. It does not log or return raw Qloo payloads or credentials.

## Validation

Unit tests use deterministic synthetic sources and invented Qloo-style transport responses to exercise conditional page recovery, call budgets, concurrency bounds, hard constraints, exhaustive-oracle Pareto trade-offs, cancellation, selected-ID revalidation, malformed data, timeout behavior, and provenance. Offline Redis-transport models exercise admission, expiry, and failure handling; the owner separately verified a five-request atomic reservation on a disposable Upstash key. The result records eligible shared-candidate counts by domain for **redacted** live evaluation. Browser tests exercise alternatives, evidence sections, repaired plans, no-solution gaps, program timing, and missing live credentials. Owner-observed P1 established one genuine no-path outcome, and the separate artist-only Bridge run established filtered coverage with unverified compatibility. A complete three-domain live path, human acceptance, provider per-source control, and public deployment remain unverified.
