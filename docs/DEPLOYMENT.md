# Free-tier deployment preparation — not authorization to deploy

The repository contains a Next.js Node runtime app (`/api/plan` is a server route), a Vercel framework configuration, and a synthetic development mode. The owner has observed authenticated Artist Search, Movie Insights, and Book Insights item metadata; the repaired Book production path and a complete two-audience live journey remain unverified end to end. No public deployment or shared Redis connection has been validated. A free account may be suitable for a bounded demonstration only after its current terms, quotas, and application behavior are checked by the account owner. In particular, [Vercel Hobby is for personal, non-commercial use](https://vercel.com/docs/plans/hobby), and its [Git organization import restriction](https://vercel.com/docs/limits) may affect this repository. Choose an eligible host before requesting deployment approval.

## Configuration

Publish a reviewed candidate only through the separately authorized [feature-branch procedure](PUBLICATION.md). Bridge Discovery remains an [unexecuted research protocol](BRIDGE_EXPERIMENT.md); it does not change the production route or its shared quota guard.

1. Deploy the existing `feature/crossfade-mvp` commit only after review. Do not merge `main` as part of setup.
2. Keep `QLOO_API_KEY` in the hosting provider's **server-side secret settings**. Never use `NEXT_PUBLIC_`, a repository file, browser storage, or a build log for this value. The current hackathon-key flow permits only `https://hackathon.api.qloo.com`; leave `QLOO_API_ORIGIN` unset or set it to that exact origin, and stop for contract review if the issuer provides another host. Keep `QLOO_LIVE_ENABLED=0` (or unset) until the authenticated and public-abuse gates below pass. Synthetic mode needs no key or Redis.
3. Build with `npm ci && npm run build`, start using the platform's Next.js Node integration or `npm run start`, and require HTTPS on the public hostname. Do not use a static export for `/api/plan`.
4. Claim a [$0 Upstash Redis database](https://upstash.com/pricing/redis) under the account owner's control. Do not use an unclaimed temporary database for a live demo. Put its HTTPS REST URL and **standard write token** in server-only `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`; the application accepts only `https://*.upstash.io` origins. Never put the token in a client variable or URL query. Upstash's [REST API supports POSTed Redis commands and scripting](https://upstash.com/docs/redis/features/restapi). The code makes one atomic `EVAL` reservation before any live Qloo call. Missing or unhealthy Redis fails closed with 503; an exhausted shared budget returns 429.
5. Obtain the issued Qloo account's real request allowance. Set `QLOO_LIVE_PLANS_PER_HOUR` to an integer from 1 to 10 that is **no larger than** `floor((remaining hourly Qloo attempts allocated to this app) / 24)`. Reserve capacity for other uses of the key. Each admitted planner run can make up to 24 retry-inclusive Qloo attempts; the Redis counter conservatively charges a full run even if fewer attempts occur. A 60-minute window begins with the first accepted run and is shared by all instances using the same database/key. If the allowance is unknown or below 24 attempts, leave live planning disabled.
6. On the chosen public host, configure a provider-enforced per-source rule for `POST /api/plan` before enabling live mode. For a Vercel deployment, start with an [IP-keyed WAF rate rule](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) of no more than five planning requests per minute per provider-observed source IP, then test allowed traffic, a sixth-request 429, and NAT/shared-IP behavior on the actual hostname. Adjust only after observing legitimate demo traffic and quota consumption. Application code must not use caller-supplied `X-Forwarded-For`, `X-Real-IP`, or `Origin` as authenticated identity. The app's process-local emergency windows are now separate: 60 synthetic or 15 live plans per minute per instance. They still allow one client to exhaust a mode's local window; the provider rule is mandatory. The atomic Redis budget is an independent cross-instance ceiling, not a per-source rule. No provider rule or Redis instance has been created or verified.
7. Restrict deployment logs to safe status/error codes. Do not log Qloo request headers, raw responses, full user interests, Redis tokens, or secrets. Monitor 429, timeout, and upstream errors without exposing payloads. A cross-request plan cache is deferred until privacy, key scoping, and expiry are specified and tested.

## Independent release gates

- **Authenticated integration:** The owner has completed the bounded Search/Movie/Book shape diagnostic. After separate account-owner approval and shared-quota setup, follow the [full live journey protocol](LIVE_JOURNEY.md); repeat the [bounded smoke](QLOO.md) only for a new contract question. Record counts/statuses, not raw responses or credentials. The observed shapes do not establish duration minutes or useful shared-entity coverage.
- **Shared quota:** Verify the actual Redis REST host, token, atomic reservation, expiry, 429 ceiling, and fail-closed behavior with the account owner's provider. Confirm the chosen ceiling against the issued Qloo quota. Offline mocks alone do not satisfy this gate.
- **Scheduling:** Obtain trustworthy film runtime in minutes and rating independently before treating a conceptual result as a duration-verified schedule. Check rights, availability, and venue separately.
- **Public deployment:** After rate controls are in place, verify HTTPS, origin behavior, error states, mobile layout, and synthetic/live provenance on the actual public URL. This is a distinct gate from local or authenticated API testing.
- **Activation:** Only after those checks, the account owner may set `QLOO_LIVE_ENABLED=1` server-side. Revert it to `0` if rate limits, response contracts, or safety controls fail.
- **Submission:** Update the Devpost text and PR validation record with only observed results; the account owner makes the final submission.
- **Public repository:** The 2026 [official rules](https://qloo.devpost.com/rules) require a public repository with working source, run instructions, and an open-source license visible at the repository top/About section. The repository is public, but its default `main` currently contains only `LICENSE`; code and `README.md` are on the feature branch. Give judges a direct feature-branch URL if this remains unmerged, and confirm that this satisfies the organizer's repository requirement. A reviewed merge or default-branch change would improve the root landing page but needs separate authorization.

No paid API, hosted database, or LLM service is required for the local synthetic demonstration. The proposed shared store has a $0 tier at the time of writing; the owner must confirm its current terms and remain on that tier. If no suitable no-cost shared limit is available, keep the public live endpoint disabled. A controlled judge demo still requires an explicit key and shared guard configuration under the current route code.
